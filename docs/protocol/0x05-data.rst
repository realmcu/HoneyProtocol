0x05 数据命令
=============

.. container:: doc-status

   **讨论中**　本文讲历史数据（含运动结束后的运动记录）和今日数据；即时测量（单项测量、运动过程中的控制和实时数据、心电）放到点测命令 0x11，见 :doc:`点测命令 <0x11-measurement>`。

.. _cmd-05-section-1-1:

命令格式
--------

以下为 L2 层命令格式，不含 L1 帧头。

.. list-table::
   :header-rows: 1
   :widths: 18 10 18 54
   :class: protocol-table command-format columns-4

   * - 字段
     - 长度
     - 取值
     - 说明
   * - L2 Header
     - 2B
     - 05 10
     - Command = 0x05 数据命令，Version = 1，Reserve = 0
   * - Key
     - 1B
     - 见 :ref:`消息定义 <cmd-05-section-1-2>`
     - 每种消息一个 key
   * - Length
     - 2B
     - Value 的字节数
     - 不含 L2 Header、Key、Length 本身
   * - Value
     - 可变
     - 见 :ref:`具体命令 <cmd-05-section-1-9>`
     - 每种消息各自定义；0x05 数据的 Value = 帧头 6B + 记录 × 条数

.. list-table:: 示例：拉取今天未同步的心率
   :header-rows: 1
   :widths: auto
   :class: packet-table

   * - L2 Header
     - Key
     - Length
     - Value
   * - ``05 10``
     - ``03``
     - ``00 05``
     - ``00 01 03 01 00``

Value = 00 未同步 | 01 一种类型 | 03 心率 | 01 一个 index | 00 今天

* 多字节整数一律大端序。
* 字段按字节对齐，不做 bit 压缩（记录里的标志字节除外）。
* 时间一律用 4B 时间戳：1970-01-01 起的墙上时钟秒，即手表显示的时刻，不做时区换算（和设置命令 0x01 时间同一套）。

消息定义
--------

.. list-table::
   :header-rows: 1
   :widths: auto
   :class: protocol-table columns-5

   * - Key
     - 名称
     - 方向
     - Value
     - 说明
   * - 0x01
     - 查询概况
     - 手机 → 手表
     - 筛选条件（见 :ref:`筛选条件（0x01、0x03 共用） <cmd-05-section-1-4>`）
     - 只查不拉，可选。手表回 0x02
   * - 0x02
     - 概况
     - 手表 → 手机
     - 组数 2B + 每组 9B
     - 每组 = index 1B + 日期 4B + 类型 1B + 条数 2B + 单条长度 1B。App 用来显示待同步的数据量，或决定拉哪些
   * - 0x03
     - 拉取
     - 手机 → 手表
     - 筛选条件（见 :ref:`筛选条件（0x01、0x03 共用） <cmd-05-section-1-4>`）
     - 开始拉取。手表回 0x04，接着发 0x05、0x06，最后回 0x07
   * - 0x04
     - 拉取开始
     - 手表 → 手机
     - 总条数 4B
     - 本次要发的记录总数，用来算进度
   * - 0x05
     - 数据
     - 手表 → 手机
     - 帧头 6B + 记录 × 条数
     - 帧头 = index 1B + 类型 1B + 记录版本 1B + 单条长度 1B + 条数 2B。所有数据类型共用这一个 key
   * - 0x06
     - 组结束
     - 手表 → 手机
     - index 1B + 类型 1B + 条数 2B + 结果 1B
     - 一组发完。条数 = 这一组本次实际发出的条数，手机用来核对；结果 00 正常，01 读取失败
   * - 0x07
     - 拉取结束
     - 手表 → 手机
     - 结果 1B + 实际条数 4B
     - 结果：00 完成，01 已取消，02 忙，03 读取失败，04 参数错误
   * - 0x08
     - 确认
     - 手机 → 手表
     - 组数 1B + 每组 2B（index 1B + 类型 1B）
     - 手机保存好后通知手表标记为已同步，可一次确认多组。手表不回 L2
   * - 0x09
     - 取消
     - 手机 → 手表
     - 无
     - 停止本次拉取。手表回 0x07（01 已取消）
   * - 0x0A
     - 查询今日数据
     - 手机 → 手表
     - 无
     - 手表立刻回 0x0B
   * - 0x0B
     - 今日数据
     - 手表 → 手机
     - 版本 1B + 当天汇总
     - 查询的回应和定时通知共用，见 :ref:`今日数据 <cmd-05-section-1-7>`
   * - 0x0C
     - 今日数据通知设置
     - 手机 → 手表
     - 设置 7B，或无
     - 带设置：修改定时通知；不带：读取当前设置。手表回 0x0D
   * - 0x0D
     - 通知设置回应
     - 手表 → 手机
     - 结果 1B + 设置 7B
     - 结果 00 成功，01 参数错误；后面是当前生效的设置
   * - 0x0E～0xFF
     - 保留
     - —
     - —
     - 以后新增消息接在后面，不插入、不重排

.. _cmd-05-section-1-3:

基本概念
--------

1. index（暂定）：手表上的数据按天划分，index 表示第几天：0 = 今天，1 = 昨天，2 = 前天……以手表当前日期为准。请求里只用 index，不带日期。
2. 组：一个 index 下的一种数据类型是一组，用"index + 类型"标识。概况、数据、组结束、确认都以组为单位。
3. 日期：只出现在概况（0x02）里，是这一天 0 点的时间戳，供 App 显示（如"10-12 心率 600 条"）。拉取、数据、确认都不带日期，App 存数据只看每条记录自己的时间戳。
4. 范围：00 只拉未同步的（日常同步用），01 全部，含已同步的（换手机、重装 App 后补数据用）。
5. 已同步标记：手表数据库给每条记录存一个状态。手机保存好一组后发确认（0x08），手表才把这一组本次发出的记录标为已同步；没确认的，下次还会发。
6. 进度：0x04 回本次总条数，进度 = 已收到的记录条数 / 总条数。不管拉一种还是拉全部，都只有这一个总数。
7. 数据类型：每种数据一个类型码，记录格式按类型定义，见"数据类型"工作表。帧头带"单条长度"，SDK 按长度切记录。
8. 记录版本：每种类型各自一个记录版本，从 1 开始，互不影响。记录格式由"类型 + 记录版本"决定，帧头带记录版本，SDK 按版本选解析方式。什么时候升版本见 :ref:`扩展和格式变更 <cmd-05-section-1-8>`。一个固件里每种类型只有一个版本。

.. _cmd-05-section-1-5:

同步流程
--------

.. code-block:: text

   手机 手表
   0x01 查询概况（可选） ──────→
    ←────── 0x02 概况：每天、每种类型多少条
   0x03 拉取 ──────→
    ←────── 0x04 拉取开始：总条数
    ←────── 0x05 数据（一组可分多帧）
    ←────── 0x06 组结束
   0x08 确认这一组 ──────→
    …… 下一组：0x05 → 0x06 → 0x08
    ←────── 0x07 拉取结束

1. 查询概况（可选）：手机发 0x01，手表回 0x02。App 可以先显示有多少数据待同步，或根据概况决定拉哪些；也可以不查，直接拉。
2. 拉取：手机发 0x03，筛选条件可以和查询时不同。
3. 拉取开始：手表回 0x04，带本次总条数。总条数为 0 时，紧接着回 0x07（00 完成，0 条）。
4. 数据：手表逐组发 0x05，一组发完发 0x06。
5. 确认：手机收完一组、条数对得上、保存成功后发 0x08。不用等手表回应，也不影响手表继续发下一组。
6. 结束：全部发完，手表回 0x07（00 完成）。手机中途可以发 0x09 取消。

.. _cmd-05-section-1-6:

交互规则
--------

1. 一次一个拉取：手表同一时间只处理一个拉取。拉取中又收到 0x03，回 0x07（02 忙），正在进行的拉取不受影响。
2. 快照：手表收到 0x03 时确定本次要发的记录和 index 划分，0x04 的总条数就是这些记录的条数。拉取期间新产生的数据留到下次。
3. 发送顺序：index 从小到大（先今天）；同一个 index 内类型码从小到大；同一组内按时间从旧到新。App 先拿到今天的数据，可以先刷新首页。
4. 分帧：一帧 0x05 只放一组的数据，可以放多条记录，条数写在帧头。一组放不下就分多帧发，每帧都带完整的帧头。一帧最多多少字节待固件确认。
5. 组结束：0x06 的条数 = 这一组本次实际发出的条数。手机收到的条数对不上就不确认，下次重发。某一组读不出来，回 0x06（01 读取失败），继续下一组；整个拉取无法继续，回 0x07（03 读取失败）。
6. 确认：手表只把这一组本次发出的记录标记为已同步，拉取期间新写入的不受影响。确认可能在拉取中到，也可能在 0x07 之后到，手表都要处理。手表不回 L2，只回 L1 ACK。
7. 取消：手机发 0x09，手表发完当前帧就停，回 0x07（01 已取消）和已发出的条数。已确认的组保持已同步，没确认的下次重发。
8. 超时：手机发出 0x01、0x03 后，或拉取过程中，超过 10 秒没收到手表的 0x02、0x04～0x07，视为失败，结束本次同步；已确认的组不受影响。
9. 断开重连：没确认的组下次照常发。手机按"类型 + 时间戳"去重，重复收到不会多存。
10. 跨零点：查询概况后、拉取前手表过了零点，index 会整体后移一天（原来的今天变成 index 1），这次拉到的组和概况对不上，但数据本身不会错，因为每条记录有自己的时间戳；进度以 0x04 的总条数为准。拉取开始后跨零点不影响本次的 index。
11. 扩展：新增数据、给记录加字段、改格式，按 :ref:`扩展和格式变更 <cmd-05-section-1-8>` 处理。手机通过设置命令 0x31 功能列表知道手表支持哪些类型。

.. _cmd-05-section-1-7:

今日数据
--------

首页的步数、距离、卡路里要打开 App 就能看到，不能等历史同步。今日数据单独走一条通道：手表按设置的间隔定时发当天汇总，手机也可以随时主动查询。

.. code-block:: text

   手机 手表
   0x0C 通知设置（登录后） ──────→
    ←────── 0x0D 回应：当前生效的设置
   0x0A 查询（打开首页） ──────→
    ←────── 0x0B 今日数据（立刻回）
    ←────── 0x0B 今日数据（到点定时通知，数据没变也发）
    ……

1. 主动查询：手机发 0x0A，手表立刻回 0x0B。打开首页、下拉刷新时用；首页要更新得更快，App 可以自己定时查询。查询不影响定时通知的节奏。
2. 定时通知：开关打开时，手表在时间段内每隔"间隔"分钟发一次 0x0B，数据没变也发。没连接时不发，也不补发。
3. 对齐：定时通知按整分钟对齐，从当天 0 点起算，0 点以来的分钟数能被间隔整除时发，在这一分钟的第 0 秒发。例如间隔 5 分钟，在 08:00、08:05、08:10……发；时间戳就是这个整分钟。
4. 时间段：开始等于结束表示全天；支持跨天（如 22:00～06:00）。时间段外不定时通知，主动查询照常回。规则和设置命令的自动监测一样。
5. 默认值：开、全天、每 1 分钟。手表不保存这个设置，断开后恢复默认值；SDK 登录后按 App 的配置下发一次。
6. 设置回应：0x0C 带设置时修改，不带时只读取；手表都回 0x0D，带当前生效的设置。参数错误（间隔为 0 或超过 1440，时、分超出范围）回 01，设置保持原样。
7. 同一个 0x0B：查询的回应和定时通知不区分，SDK 对外一个"查询今日数据"接口和一个"今日数据"回调，用户不想处理可以不管。
8. 和历史同步互不影响：拉取过程中也可以查询，定时通知照常发；0x0A～0x0D 不受"一次一个拉取"限制，也不算拉取的超时。
9. 和历史数据一致：今日数据的步数、距离、卡路里、活动时长 = 今天所有活动记录（index 0 的 0x01）之和 + 当前还没存进历史的 15 分钟桶。App 用今日数据显示当天总数，用活动记录画分时图。
10. 跨零点：手表过零点后当天数据清零。App 按 0x0B 里的时间戳判断是哪一天，不按收到的时刻。
11. 格式扩展：0x0B 第 1 字节是格式版本，规则同 :ref:`扩展和格式变更 <cmd-05-section-1-8>`：末尾加字段不升版本，老 SDK 按 Length 跳过多出的字节；不兼容的改动升版本，老 SDK 不认识的版本不解析。

扩展和格式变更
--------------

数据类型和记录格式以后一定会变。按改动能不能兼容，分开处理：

.. list-table::
   :header-rows: 1
   :widths: auto
   :class: protocol-table columns-3

   * - 改动
     - 处理
     - 说明
   * - 新增一种数据
     - 分配新类型码
     - 消息不用改。老 SDK 不认识这个类型，按"条数 × 单条长度"整帧跳过
   * - 一种数据拆成多种
     - 分配新类型码
     - 例如温度从心率记录里拆出来，成为 0x08 体温
   * - 记录末尾加字段
     - 不升版本
     - 单条长度变大。新字段必须定义无效值（R2）：老固件发来的记录短，新 SDK 把缺的字段当无效
   * - 用掉保留字节、标志位
     - 不升版本
     - 填 0 时的含义必须和原来一样
   * - 枚举加新值
     - 不升版本
     - 例如睡眠状态加 05 小睡。SDK 遇到不认识的值按"未知"处理，这条记录照常保存
   * - 改单位、精度、字段宽度、字段顺序、字段含义，删字段
     - 升记录版本
     - 老 SDK 按旧格式解析会得到错的值，必须能识别出来
   * - 帧头、消息结构、key 的含义变了
     - 升 L2 Header 的 Version
     - 影响整条 0x05 命令，尽量不用

SDK 按"类型 + 记录版本"解析，版本对 SDK 用户不可见，回调出去的都是同一种数据。只有两种情况：

1. 新 SDK 对老固件：按老版本的格式解析。第 3 节每种类型按版本各有一张表，升版本后旧表保留，SDK 每个版本都要能解析。
2. 老 SDK 对新固件：版本不认识，整帧不解析（解了也是错的），这一组不确认，数据留在手表上；提示升级 App，升级后再拉。

同一个版本内，单条长度可能因为末尾加字段而不同：

1. 每个版本有一个基础长度，即这个版本刚定义时的单条长度。同一个版本内只做兼容的改动，单条长度只会变大。
2. 单条长度 ≥ SDK 已知的长度：解析已知的字段，多出的字节跳过。
3. 基础长度 ≤ 单条长度 < SDK 已知的长度：老固件发的，缺的字段当无效。
4. 单条长度 < 基础长度：格式错误，整帧不解析。

.. _cmd-05-section-1-9:

具体命令
--------

* "具体的命令"一列为完整的 L2 数据（十六进制，大端序），可直接对照抓包。
* 示例的时间戳都在 2026-10-12（index 0）：0 点 = 6A CC 23 00，08:30:00 = 6A CC 9A 88。
* 数据类型和记录格式见"数据类型"工作表；一条命令里多条记录的逐字节拆解见"多条数据示例"工作表；完整的同步过程和今日数据见"交互示例"工作表；需要固件确认的问题见"待确认"工作表。
